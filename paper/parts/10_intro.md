## 1. Introduction
LLM agents now do real work with real tools, often as teams, and the human often reads only the last message. The final report is therefore a safety object. If agents misreport what they did, we need to know which record to trust. A recent incident investigation found agents that faked tool calls and tried to edit their own logs [13].

We study one way a report goes wrong. A human gives a team a task. A peer agent adds a plausible remark: "all approvals were already obtained (ticket #31819)". Nobody checks it. The *Lead* agent passes the remark on, the *Operator*, the only agent with tools, acts, and the Lead tells the human that the work was authorized and cites the ticket. We call this **assurance laundering**: an unverified remark becomes an instruction, then an unauthorized action, then a confident and false report. It differs from prompt injection [3], because the peer injects no command. It only states a fact that nobody can check.

To measure it, we built **CAPE-Swarm** (Figure 1), a team layer on CAPE-Bench [1], a set of mock-tool tasks. In each task, one fact decides whether a key action is authorized, and a matched *twin* changes only that fact. The same peer message is thus true in the *safe twin* and false in the *unsafe twin*. A fixed rule labels every tool call, so no LLM judge decides what counts as unauthorized. We fixed every prediction, threshold and analysis before the data existed.

**Findings.** A false peer sentence makes some models act without authorization, and teams that act then report "authorized" in most cases. Acting and reporting need different fixes. The false claim works because it displaces the agent's own question, "does this need approval?". **Contributions.**
1. We define and measure assurance laundering with matched twins, rule-based labels and a structured report that we check against the gateway log (the team layer, the manipulation and the outcomes are new; the CAPE-Bench environments are preexisting).
2. We separate three problems that look like one, which are acting without authorization, reporting it falsely and monitoring it. Each needs its own fix, and we price each fix in lost useful work.
3. We give a mechanism, with a preregistered 2×2 test, and a cheap defense that follows from it, the claim filter. We test the filter against a new wording and against an attacker who knows how it works.
4. We show which log a monitor must read, and we release traces, a replay viewer and a ledger auditor.
