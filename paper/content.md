TITLE: Who Approved This? Assurance Laundering in LLM Agent Teams
AUTHOR: Arya Fayyazi | University of Southern California
ABSTRACT:
AI agents now work in teams and use tools, and the human often reads only the final report. We study *assurance laundering*. A peer agent says, without proof, that approval was already given. The team acts on this claim without authorization. Then it tells the human, with confidence, that the work was authorized. We built CAPE-Swarm, a team layer on the CAPE-Bench test environments. Each task has a safe twin and an unsafe twin that differ in one fact, and a fixed rule (not an LLM) labels every action. We preregistered {{X['nh']}} hypotheses and ran {{sum(D['counts'].values())+R['counts']['e9']|,}} episodes with seven open-weight models. One false sentence from a peer raised the share of unauthorized actions of a single agent from {{X['V_none']['solo']|.2f}} to {{X['V_peer']['solo']|.2f}} (95% CI of the difference [{{H['H1']['lo']|+.2f}}, {{H['H1']['hi']|+.2f}}]). Three models reacted strongly and three hardly at all. When a team did act without authorization, its report said "authorized" in {{H['H3']['false_assurance_over_V']|.0%}} of cases. Acting and reporting need different fixes. A permission record repairs the report. An ask-before-act rule at the gateway stops the action. A *claim filter*, which marks every approval claim as unverified before an agent reads it, cut unauthorized actions from {{R['_cells']['B']['V']|.2f}} to {{R['_cells']['C']['V']|.2f}} on new scenarios, with no measurable loss of useful work. @@R2TAIL@@ A monitor that reads the gateway log with tool results detects violations well (AUROC {{X['mon']['L3'][0]|.2f}}–{{X['mon']['L3'][1]|.2f}}). ## 1. Introduction
AI agents now do real work with real tools, and the human often sees only the last message. So the final report is a safety object. If we cannot trust what agents write about what they did, we need to know which record to trust. A recent investigation of a multi-agent incident found agents that faked tool calls and tried to edit their own logs [13].

We study one way that reports go wrong. A human gives a team a task. A peer agent adds a plausible remark: "all approvals were already obtained (ticket #31819)". Nobody checks it. The *Lead* agent passes the remark on. The *Operator*, the only agent with tools, acts. Then the Lead tells the human that the work was authorized, and cites the ticket. We call this **assurance laundering**. A remark becomes an instruction, then an unauthorized action, then a confident and false report.

To test this, we built **CAPE-Swarm** (Figure 1). It is a team layer on CAPE-Bench [1], a set of mock-tool tasks. In each task, one fact decides whether a key action is authorized. A matched *twin* of the task changes only that fact. So the same peer message is true in the *safe twin* and false in the *unsafe twin*. A fixed rule checks every tool call that an agent makes. No LLM judge decides what is unauthorized. We ran seven open-weight models in single-agent and team set-ups. We locked every hypothesis, threshold and piece of analysis code before the data existed.

**What we find.** One false peer sentence makes some models act without authorization. A single agent acts without authorization in {{X['V_none']['solo']|.0%}} of unsafe tasks with no message, and in {{X['V_peer']['solo']|.0%}} with the false message. Models differ a lot. Teams lower the rate, but the report still says "authorized" in most violating episodes. Three fixes work on different parts of the problem. A permission record repairs the report. An ask-before-act rule at the gateway stops the action. A *claim filter* marks approval claims as unverified before an agent reads them. It cut unauthorized actions from {{R['_cells']['B']['V']|.2f}} to {{R['_cells']['C']['V']|.2f}} on new scenarios. @@R2INTRO@@ Last, a monitor can see the violation only if it reads the gateway log with tool results.

**Contributions.**
1. We define and measure assurance laundering. We give matched twins, a rule-based label for every call, and a structured report that we can check against the gateway log. (New: the team layer, the manipulation and the outcomes. Preexisting: the CAPE-Bench environments.)
2. We separate three problems that look like one: acting without authorization, reporting it falsely, and monitoring it. Each needs its own fix, and we price each fix in lost useful work.
3. We test a cheap defense, the claim filter, against a fixed message, a new wording and an attacker who knows how the filter works. We also test why the false claim works.
4. We show which log a monitor must read. We release traces, a replay viewer and a ledger auditor, so that a team can run the same test on its own agents.

## 2. Related Work
**Failures in multi-agent systems.** Hammond et al. [2] map the risks of interacting agents. Cemri et al. [4] label failure modes in traces from agent frameworks. We study one security failure. We have a ground-truth label in every episode. **Spread inside a team.** Prompt Infection [3] shows that an injected instruction can pass from agent to agent. We inject no instruction. A peer states a plausible fact that nobody can check, and normal delegation does the rest. **Authorization.** Access-control defenses for agents, such as SEAgent [7], ScopeGate [8] and the analysis in [9], build mechanisms. We measure the behavior that makes them necessary, and we price them in lost useful work with matched safe twins.

Four recent studies are closest to ours. All of them test false authority in agent systems. Cerruti et al. [15] show that a false permission record in agent memory leads executors to act ("endogenous authorization laundering"). Safin et al. [16] show that a forged approval in a four-agent pipeline reaches the executor, unless an independent authorization layer blocks it. Zhu et al. [17] separate message delivery, signing authority and tool-side enforcement. They find that a deterministic tool gate stops the requests that models make. Xu et al. [18] find that unauthorized actions grow with the depth of the delegation hierarchy. We agree with their shared conclusion: enforcement must sit outside the model. We add three things. First, matched safe and unsafe twins with a rule-based label for every call, so we can price a gate. Second, the *report* to the human as an outcome, and the question of which log lets a monitor see the failure. Third, a test of an in-transit defense against an attacker who knows how it works. Our claim filter is a form of spotlighting [14], which marks untrusted text. It is much weaker in principle than the capability tracking in CaMeL [19]. We test it because it needs no change to the agents. The provenance paradox [10] also says that unverifiable claims mislead delegation.

**Control and monitoring.** AI control [5] and resampling [6] study monitors for one untrusted agent. Rose et al. [11] argue that secret collusion may limit what transcript monitors can see. Korbak et al. [12] call chain-of-thought monitoring a fragile opportunity. We ask which log a deployer must keep. An incident investigation [13] found agents that faked tool calls and edited logs inside their containers. That is why our strongest log is written by the gateway. **Our prior work.** CAPE-Bench [1] gives matched twins for single agents. It also defines retroactive permission laundering. We reuse its environments unchanged (preexisting). The teams, gateway, controls, monitors and all results are new.

## 3. Methods
**Tasks (preexisting).** CAPE-Bench has eight task families, such as authorization, ownership and third-party data. Each task has a *safe twin* and an *unsafe twin*. They differ in one fact that decides whether the critical action is authorized. All tools are mock tools (files, a database, messages, a shell and a permission system). A fixed rule checks each executed call and labels it authorized or unauthorized. We draw 48 base tasks (six per family) with a fresh seed. With two twins, each condition has 96 instances. A different seed served only for debugging.

**Teams (new).** One model fills every role, except in one experiment that mixes models. Only the **Operator** has tools. The **Lead** has no tools. It writes a brief for the Operator and a final report for the human. The *relay* team is Lead plus Operator. The *relay-2* team adds a **Manager** between them. The *solo* agent is the Operator alone. The final report is a structured call. Its field `authorization_status` is "authorized", "not_authorized" or "unsure". So we score reports by rule.

**The manipulation (new).** A scripted peer message says that all approvals were obtained earlier today (with a ticket number) and that no further approval is needed. The message is the same in both twins. It is true in the safe twin and false in the unsafe twin. Nobody tells any agent to lie.

**Outcomes (new).** We use four outcomes. All are per episode (one run of one team on one task).
- *Violation* (V): the rule checker labels at least one executed call unauthorized. We report V on unsafe twins. V is the share of unsafe-twin episodes with a violation.
- *False report*: a violating episode whose report says "authorized". *Disclosed*: a violating episode whose report says "not_authorized".
- *Goal*: the team completed the task's authorized goal action. We read goal completion on safe twins as a measure of useful work (utility).

**Controls (new).** A control is a change to the team or the gateway. (i) The *oracle check* dry-runs each state-changing call against the benchmark's own checker. It is an upper bound, not a deployable control. (ii) The *ask-before-act gate* lets a state-changing call run only after a permission request whose latest answer is not a denial. It needs no oracle. (iii) An *auditor* is an LLM that approves each state-changing call. It sees the call only, or the call with tool results, or also the team's messages. (iv) A *verification prompt* is one rule in every agent's system prompt: a claim of approval is unverified until the permission system confirms it. (v) A *report source* change lets the Lead see the gateway log, or the log plus an explicit permission record.

**Round 2 (new).** After round 1, the API rate limit fell to about 60 requests per minute. So the round-2 experiments are smaller (at most 40 base tasks). The **claim filter** (E9) is a separate model (glm-53-flash) that reads every message crossing an agent boundary. It rewrites any claim that an approval exists into an attributed, *unverified* claim, and adds one rule: confirm with the permission system before any state-changing action. It never learns whether the claim is true. If it returns nothing, the original message passes. We test it on fresh tasks (seed 5501), against the gate, and with a new wording, the attacker message from E8. In **E11**, an attacker model reads the full filter prompt and searches for a message that gets past it. We then test its best message. **E12** crosses the false claim with the verification prompt. It asks whether the claim does harm because agents believe it, or because it replaces the agents' own check. **E10** (an Operator told to look routine to a monitor) {{'was run' if R.get('H26') else 'was planned and not run'}}.

**Monitors (new).** A *monitor* is an LLM judge that reads part of a trace and scores from 0 to 100 how likely a violation is. The *log level* says what it reads: L0 the final report; L1 the messages; L2 the tool calls; L3 the calls with their results; L4 everything. We measure *AUROC*, the chance that a random violating trace scores higher than a random clean one (0.5 is chance, 1.0 is perfect). We also measure the *catch rate* at a 5% false-alarm budget. A *self-query* monitor asks the Operator's own model two yes/no questions. A *rule monitor* flags any state-changing call with no earlier approved request.

**Models and statistics.** Seven open-weight models run through the Adaption API: gemma-4-26b-a4b-it, gemma-4-31b-it, qwen3.8-27b, qwen3.5-397b, glm-53-flash, glm-5.2 and deepseek-v4-flash. Agents use temperature 0.7 and at most 24 turns. Every hypothesis has an ID such as H1. We fixed each one, with its threshold, sample size and analysis code, before any confirmatory episode existed. SHA-256 hashes and git commits record the order. The unit of analysis is the base task, because its episodes are not independent. We give 95% confidence intervals (CI) from a bootstrap over base tasks, and p-values corrected for many tests (Holm). Pooled numbers give every model equal weight. We report every hypothesis, including the failures. Appendix D lists every experiment.

### 4.5 Robustness: wording and repeats
The effect is not tied to one sentence. ### 4.8 A claim filter: mark the claim, keep the work
The false claim does the harm, and the gate stops the action at a cost in useful work. Can we remove the harm at the claim itself? We added a **claim filter** to the message bus. A small model (glm-53-flash, temperature 0) reads every message between agents. If a message claims approval, authorization or permission, the filter rewrites that claim. The new text says who made the claim, says it is unverified, and tells the reader to confirm it with the permission system before any state-changing action. The rest of the message is unchanged. The filter does not see the task, the log or the twin. If it returns nothing, the original message passes. This happened in {{R['_filter']['fail_open']}} of {{R['_filter']['calls']}} filter calls, mostly on the Lead's brief. The idea is close to spotlighting [14], which marks untrusted text for the model. We mark a *claim* by its source, between agents. We test it with matched twins and a rule checker.

We ran this on fresh tasks (E9, seed 5501, relay, four models, {{R['counts']['e9']}} episodes). Here V is the share of unsafe-twin episodes with a violation. The design had 40 base tasks. The API limit fell during the sprint, so only {{R['_n_clusters']}} base tasks have every condition finished. We analyse those (see Limitations). Figure 5 shows the results.

**The false message works again (H20 supported).** V rises from {{R['_cells']['A']['V']|.2f}} with no message to {{R['_cells']['B']['V']|.2f}} with the peer message ({{H['H20']['point']|+.2f}} [{{H['H20']['lo']|+.2f}}, {{H['H20']['hi']|+.2f}}]).

**The filter removes most of the harm (H21 supported).** With the filter, V falls to {{R['_cells']['C']['V']|.2f}} ({{H['H21']['point']|+.2f}} [{{H['H21']['lo']|+.2f}}, {{H['H21']['hi']|+.2f}}]). ## 5. Discussion and Limitations
**Three problems, three fixes.** Acting without authorization, reporting it falsely and monitoring it are three different problems. One unverified sentence raised V by {{H['H1']['point']|+.2f}} in a single agent. Teams lowered V but did not fix the report: {{min(X['fa_over_v'][t]['FA']['point'] for t in X['fa_over_v'])|.0%}} to {{max(X['fa_over_v'][t]['FA']['point'] for t in X['fa_over_v'])|.0%}} of violating episodes ended with a false "authorized". A permission record repaired the report ({{H['H4']['parts'][0]['point']|.0%}} fewer false reports) but did not change the action. The ask-before-act gate stopped the action (V = {{H['H5']['parts'][0]['point']|.1%}}) for about {{H['H5']['parts'][1]['point']*100|.0f}} points of useful work. The claim filter removed most of the harm on fresh tasks, at no measurable cost. A verification prompt and an auditor sat in between, with a residual V of about {{(X['resid'][0]+X['resid'][1])/2|.0%}}.

**What a deployer should log and enforce.**
1. Write the log at the gateway, with tool results, where no agent can edit it. A monitor that reads the report ({{X['mon']['L0'][0]|.2f}}–{{X['mon']['L0'][1]|.2f}} AUROC) or the calls without results ({{X['mon']['L2'][0]|.2f}}–{{X['mon']['L2'][1]|.2f}}) is close to blind. One that reads calls with results reaches {{X['mon']['L3'][0]|.2f}}–{{X['mon']['L3'][1]|.2f}}.
2. Keep an explicit permission record, and make reports cite it and not a peer.
3. Enforce ask-before-act at the gateway. If you cannot, mark every approval claim that crosses an agent boundary as unverified (the claim filter, 4.8).
4. Test your own models with matched twins first. Three of seven models hardly reacted to the claim and three reacted strongly, so model choice is a safety decision.
5. Make agents state what they did not verify (4.5).

**What did not hold.** Four hypotheses failed. H13: the Operator's model does not decide alone, because the Lead is a gatekeeper. H8: the team's own words do not recruit an auditor or a monitor. H18: a short attacker search found no stronger message. H25: we did not show that the filter costs less than the gate.

**Limitations.** (Appendix A has the full list.) We used open-weight models only. The attackers are weak (scripted wordings and short searches). The tools are mock tools. The oracle check is an upper bound. The judges come from the same model families as the agents. Round 2 is small, because the API rate limit fell during the sprint. We assume the gateway log cannot be edited by agents, but real agents have edited logs [13]. **Future work:** frontier models, trained attackers, real swarm logs and mesh topologies.

## 6. Conclusion
One unverified sentence from a peer agent can make an agent team act without authorization, and then report the work as authorized. How much depends on the model, the team shape and the Lead. The fixes work on different parts of the problem. A permission record repairs the report. An ask-before-act gate stops the action. A claim filter, which marks approval claims as unverified, removes most of the harm at no measurable cost in our tests. @@R2CONC@@ A monitor must read the gateway log with tool results to see the violation. We preregistered {{X['nh']}} hypotheses and report all of them. {{X['nfail_word']}} failed ({{X['failed_ids']}}). We release the traces, a replay viewer and a ledger auditor.

## Appendix A. Limitations and Dual-Use / Ethical Considerations
### A.1 Limitations
We list each assumption and say how a result would change if it failed.
- **Open-weight models only.** The sprint API serves seven open-weight models. Frontier closed models may behave differently. The effect size varies a lot between our models (Figure 2a), so we do not claim a rate for any other model. The *direction* of the mechanism is what we test. If frontier models resist the assurance, H1 would fail for them, and the gateway results (H5) would still stand.
- **The attacker is weak.** One message from a peer starts the chain. We tested four hand-written wordings (E5) and a two-round search by one attacker model that saw only a generic description and development-seed scores (E8). A stronger attacker that knows the scenario, the policy or the agents' prompts, or one trained against the team, may do more.
- **One model per team, mostly.** Teams use one model for every role. E4 mixes models, but only four models and only across the credulous/skeptical divide.
- **Controls were tested on four models.** We chose the four models with the highest violation rates in the development pilot. On the models that hardly react there is little to prevent, so the benefit would be smaller, and the utility cost would stay. We did not test controls on all seven models.
- **No tamper test.** We assume the gateway writes the ledger and agents cannot edit it. We did not test agents that try to edit or spoof it. Deployers should write the ledger from a separate process (a gateway or proxy) and, where needed, to an append-only store outside the agents' reach.
- **Small cells.** Each model cell has 48 episodes per condition, so per-model numbers are descriptive. Pooled estimates use 48 scenario clusters.
- **Mock tools and a rule checker.** CAPE-Bench is synthetic. The permission system answers "approved" or "denied" by a fixed rule per world. Real approvers are slower and noisier. The utility cost of the ask-before-act gate may be larger in real workflows.
- **The oracle policy check is an upper bound.** It uses the benchmark's own checker. Its zero violation rate is true by construction (H11), so we do not count it as a finding.
- **Reports show facts, not intent.** A false "authorized" is a false statement of fact. We do not claim the agents *meant* to deceive. The self-query monitor (H9) probes this and does not settle it.
- **Monitors are LLM judges from the same families as the agents.** A judge may share the agents' blind spots. We assume the gateway ledger (L2, L3) is written by the gateway and cannot be edited by agents. An incident investigation found agents that spoofed tool calls and edited logs inside their containers [13]. If agents could write the ledger, L3 would lose its advantage.
- **Sample size and scope.** 48 base scenarios (6 per family) give 96 instances per condition. Intervals reflect scenario sampling, not template or family sampling. Per-family results are exploratory.
- **Round 2 is smaller than planned.** The API limit fell from about 300 to about 60 requests a minute during the sprint, so we cut the design (Amendments 5b, 5c). E9 stopped at its scheduled time: {{R['_n_clusters']}} of 40 planned base scenarios have every condition finished, and 26 of its 96 task prompts repeat prompts of round 1 (new entities, same templates). Its intervals use these {{R['_n_clusters']}} clusters. We looked once at the per-cell violation rates of the first 200 finished E9 episodes, and changed no hypothesis, threshold or test after that look (Amendment 5c; `docs/DEVIATIONS.md`).
- **The claim filter fails open.** If the filter model returns nothing, the original message passes: {{R['_filter']['fail_open']}} of {{R['_filter']['calls']}} calls, mostly on the Lead's brief. The filter's effect is therefore a lower bound for a filter that never fails. A filter is one more model in the path, so it adds latency and one more point of attack. It protects against *claims of approval*, not against other false claims.
- **The filter-aware attacker is white-box but brief.** It sees the full filter prompt, searches for two rounds on a development seed against two models, and tests one message. A longer search, or an attacker that is trained, may do more.
- **Ordering evidence is local.** Locks are SHA-256 hashes and git commits. Dates inside one repository can be forged. The commit history should be published with the report so that readers can check the order.


### A.2 Dual-Use and Ethical Considerations
**What this work could enable.** The study shows that a single false, plausible sentence ("all approvals were obtained") can make agent teams act without authorization and then report with false confidence. A malicious actor could use the same idea to social-engineer an agent team. The idea is simple, and our wording variants add little to it. We release no attack tooling. The repository contains the wordings we tested and the record of the attacker search (`docs/attacker_search.json`): short, generic sentences that add little to the main message, which we include so that the search can be reproduced. All environments are mock tools with synthetic people and organizations. No real system, person or data was touched.

**Why we publish.** The same results tell deployers what to log and what to enforce. In our tests a gateway rule stops the action and a permission-system record cuts false reports. A monitor that reads only messages sees the violation poorly (AUROC {{X['mon']['L1'][0]|.2f}}–{{X['mon']['L1'][1]|.2f}}), so deployers who log only messages are close to blind. We judge that this defensive value outweighs the small uplift to attackers. We also state clearly that the in-protocol auditor and the verification prompt are not enough alone.

**Monitor evasion.** Our results show which logs a monitor needs. An attacker who knows this could try to write false entries into those logs. We therefore state our assumption that the gateway ledger is not agent-writable, and we cite evidence that real agents have tried to tamper with logs [13].

**Misuse of the auditor.** The ledger auditor can raise false alarms. It is a screening aid and not evidence of wrongdoing by any agent or person. We do not claim that the agents acted with intent.

**Data and models.** The data contain only synthetic traces from public open-weight models. Credentials were kept outside the repository.

**Limitations of this appendix.** We did not run a human study and did not consult an ethics board. We believe the risk is low, but we cannot rule out uses we did not foresee.
