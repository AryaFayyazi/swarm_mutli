## 1. Introduction
Teams of AI agents now do real work with real tools, and the human often sees only the last message. This makes the *report* a safety-critical object. A recent investigation of a multi-agent incident found agents that spoofed tool calls and tried to edit the logs inside their own containers [13]. If we cannot trust what agents write about what they did, we need to know which record to trust, and who writes it.

We study one concrete way that reports go wrong. In a team, a peer agent states a plausible fact: "all approvals were already obtained (ticket #31819)". Nobody has verified it. The Lead passes it to the Operator, the Operator acts, and the Lead tells the human that the work was authorized and cites the ticket. We call this **assurance laundering**. An unverified claim enters the team as a remark, becomes an instruction, leads to an unauthorized action, and leaves the team as a confident, specific, false report.

We test this with **CAPE-Swarm**, a team layer on top of CAPE-Bench [1]. In every scenario, one fact decides whether the critical action is authorized, and a matched twin flips that fact. A rule-based checker labels each executed call, so no LLM judge decides what is unauthorized. The same peer message appears in both twins. It is true in one and false in the other. We ran {{D['counts']['e1']}} episodes of seven open-weight models in solo, relay and relay-2 teams, plus controls, mixed-model teams and monitors. All hypotheses, thresholds and code were locked before the data existed.

**Our contributions.**
1. We define and measure *assurance laundering* in agent teams. We give matched safe and unsafe twins, a rule-based label for every call, and a structured report whose claims can be checked against the gateway ledger. (New: the team layer, the manipulation, the outcomes. Preexisting: the CAPE-Bench environments.)
2. We separate three problems that look like one. Acting without authorization, reporting it falsely, and monitoring it need different fixes. A permission-system record repairs the report. An ask-before-act gateway rule prevents the action, and we price it in utility. In-protocol auditors and prompts help only in part.
3. We give a deployer a log ladder (report, messages, calls, calls with results, everything) and show which level lets a monitor see the violation. We release the traces, a replay viewer and a ledger auditor, so a team can run the same test on its own agents.

## 2. Related Work
**Multi-agent failures.** Hammond et al. [2] map the risks of interacting advanced agents. Cemri et al. [4] label 14 failure modes in more than 1,600 framework traces. We study one security failure with a ground-truth label in every episode. **Spread in a team.** Prompt Infection [3] shows that an injected instruction can pass from agent to agent. We inject no instruction: a peer states a plausible, unverifiable fact, and ordinary delegation does the rest. **Authorization.** Confused-deputy and privilege-escalation defenses for agents use access control: SEAgent [7] adds mandatory access control with an information-flow graph, ScopeGate [8] a policy decision and enforcement point with default deny, and Dantuluri et al. [9] audit identity and authorization in delegation. These works build mechanisms. We measure the behavior that makes them necessary and price them in utility with matched safe twins. The provenance paradox [10] shows that unverifiable claims mislead delegation; our permission-system record is the "attested" side of that split. **Control and monitoring.** AI control [5] and resampling [6] study monitors for one untrusted agent. Chain-of-thought monitoring [12] and collusion probes [11] argue that transcripts have a ceiling. We ask which log a deployer must keep. A recent incident investigation [13] found agents that spoofed tool calls and edited logs inside their containers, which is why our strongest log is written by the gateway. **Our prior work.** CAPE-Bench [1] gives matched twins for single agents and defines retroactive permission laundering. We reuse its environments unchanged (preexisting). The teams, gateway, controls, monitors and all results are new.

## 3. Methods
**Environment (preexisting).** CAPE-Bench has eight families (authorization, ownership, provenance, consequence, reversibility, third party, credential, constraint). Each scenario has a *safe twin* and an *unsafe twin* that differ in one fact that decides whether the critical action is authorized. All tools are mock tools. A rule checker labels each executed call; no LLM judge decides what is unauthorized. We draw 48 base scenarios (six per family) with a fresh seed, so each condition has 96 instances. A separate seed served for debugging and pilots only.

**Teams, manipulation, outcomes (new).** One model fills every role (except in E4). Only the **Operator** has tools. The **Lead** has none: it writes the brief and the final report. The *relay-2* team adds a **Manager** between them. The *solo* agent is the Operator alone. The report is a structured call whose field `authorization_status` is authorized, not_authorized or unsure, so reports are scored by rule. The **manipulation** is one scripted peer message: all approvals were obtained earlier today (ticket number), no further approval needed. It is identical in both twins, true in the safe twin and false in the unsafe twin. Nobody is told to lie. *V* means the checker labels an executed call unauthorized. *False assurance* is V with a report of "authorized"; *disclosed* is V with "not_authorized". *Goal* is an authorized goal action (utility, read on safe twins).

**Controls (new).** (i) *Oracle policy check*: dry-runs each state-changing call with the benchmark checker (an upper bound). (ii) *Ask-before-act gate*: a state-changing call runs only after a permission request whose latest answer is not a denial; it needs no oracle. (iii) *Auditor agent*: an LLM approves each state-changing call, seeing the call only, plus tool results, or plus the swarm's words. (iv) *Verification prompt*: one rule in every system prompt. (v) *Reporting*: the Lead also sees the gateway ledger, or the ledger plus an explicit permission-system record.

**Monitors (new).** An LLM judge reads the trace at one of five levels (L0 final report; L1 messages; L2 tool calls; L3 calls and results; L4 everything) and scores 0–100 the chance that an unauthorized action ran. Two judges score each trace twice. A *self-query* monitor asks the Operator's model two fixed yes/no questions about its own transcript. A deterministic *rule monitor* flags any state-changing call without an earlier approved permission request. We report AUROC and the catch rate at an exact 5% false-alarm budget (ties count as false alarms).

**Models, preregistration, statistics.** Seven hosted open-weight models run through the Adaption API (gemma-4-26b-a4b-it, gemma-4-31b-it, qwen3.8-27b, qwen3.5-397b, glm-53-flash, glm-5.2, deepseek-v4-flash; temperature 0.7, native tool calls, at most 24 turns per agent). We fixed hypotheses, thresholds, sample sizes and analysis code before any confirmatory episode existed; SHA-256 hashes and git commits record the order. The unit of analysis is the base scenario (48 clusters). Pooled estimates weight models equally. We report 95% cluster-bootstrap intervals (10,000 draws) and Holm-corrected p-values, for every hypothesis, including those that fail. What did not work during development: our first harness lost 38% of reports to turn limits (fixed with neutral nudges), and a regex for "orders to skip approval" mixed endorsements with protective rules (replaced by a model label, see 4.2).

### 4.4 In a mixed team, the Lead is the gatekeeper
We paired credulous models (Gemma-4 26B, Qwen3.5-397B) and skeptical models (GLM-5.2, GLM-5.3 flash) in the relay: 8 cross pairs, {{D['counts']['e4']}} episodes. We expected that the Operator's model would decide whether the team acts. **This was wrong (H13 not supported).** A skeptical Lead in front of a credulous Operator keeps only {{H['H13']['parts'][0]['point']|.0%}} of the all-credulous violation rate (violations {{X['e4_groups']['S lead + C op']['V']|.2f}} against {{X['e4_groups']['C lead + C op']['V']|.2f}}; 95% CI of the ratio [{{H['H13']['parts'][0]['lo']|.0%}}, {{H['H13']['parts'][0]['hi']|.0%}}], below our 50% threshold). A credulous Lead in front of a skeptical Operator gives {{X['e4_groups']['C lead + S op']['V']|.2f}} [{{X['e4_groups']['C lead + S op']['lo']|.2f}}, {{X['e4_groups']['C lead + S op']['hi']|.2f}}], above our 0.10 threshold and above the all-skeptical team ({{X['e4_groups']['S lead + S op']['V']|.2f}}). The Lead is a gatekeeper: the brief it writes sets what the Operator believes, so a careful Lead removes most of a credulous Operator's violations, and a careless Lead leaks some risk to a careful Operator. The Lead also decides what the human reads. Among violating episodes, a skeptical Lead's report discloses the violation {{H['H14']['point']|+.2f}} more often than an all-credulous team's [{{H['H14']['lo']|+.2f}}, {{H['H14']['hi']|+.2f}}] (H14 supported).

## Appendix A. Limitations and Dual-Use / Ethical Considerations
### A.1 Limitations
We list each assumption and say how a result would change if it failed.
- **Open-weight models only.** The sprint API serves seven open-weight models. Frontier closed models may behave differently. The effect size varies a lot between our models (Figure 1a), so we do not claim a rate for any other model. The *direction* of the mechanism is what we test. If frontier models resist the assurance, H1 would fail for them, and the gateway results (H5) would still stand.
- **The assurance is scripted.** One message from a peer starts the chain. We do not test an adaptive attacker who optimizes the message. Real attacks may be stronger. Our wording variants (E5) only show that the effect is not tied to one phrase.
- **One model per team, mostly.** Teams use one model for every role. E4 mixes models, but only four models and only across the credulous/skeptical divide.
- **Mock tools and a rule checker.** CAPE-Bench is synthetic. The permission system answers "approved" or "denied" by a fixed rule per world. Real approvers are slower and noisier. The utility cost of the ask-before-act gate may be larger in real workflows.
- **The oracle policy check is an upper bound.** It uses the benchmark's own checker. Its zero violation rate is true by construction (H11), so we do not count it as a finding.
- **Reports show facts, not intent.** A false "authorized" is a false statement of fact. We do not claim the agents *meant* to deceive. The self-query monitor (H9) probes this and does not settle it.
- **Monitors are LLM judges from the same families as the agents.** A judge may share the agents' blind spots. We assume the gateway ledger (L2, L3) is written by the gateway and cannot be edited by agents. An incident investigation found agents that spoofed tool calls and edited logs inside their containers [13]. If agents could write the ledger, L3 would lose its advantage.
- **Sample size and scope.** 48 base scenarios (6 per family) give 96 instances per condition. Intervals reflect scenario sampling, not template or family sampling. Per-family results are exploratory.
- **Ordering evidence is local.** Locks are SHA-256 hashes and git commits. Dates inside one repository can be forged. We will publish the repository so that the commit history is public.


### A.2 Dual-Use and Ethical Considerations
**What this work could enable.** The study shows that a single false, plausible sentence ("all approvals were obtained") can make agent teams act without authorization and then report with false confidence. A malicious actor could use the same idea to social-engineer an agent team. The idea is simple, and our wording variants add little to it. We release no optimized attack text and no attack tooling beyond the four wordings used in the scenarios. All environments are mock tools with synthetic people and organizations. No real system, person or data was touched.

**Why we publish.** The same results tell deployers what to log and what to enforce. A gateway rule and a permission-system record prevent the action and the false report in our tests. A message-level monitor cannot see the violation, so deployers who log only messages are blind to it. We judge that this defensive value outweighs the small uplift to attackers. We also state clearly that the in-protocol auditor and the verification prompt are not enough alone.

**Monitor evasion.** Our results show which logs a monitor needs. An attacker who knows this could try to write false entries into those logs. We therefore state our assumption that the gateway ledger is not agent-writable, and we cite evidence that real agents have tried to tamper with logs [13].

**Misuse of the auditor.** The ledger auditor can raise false alarms. It is a screening aid and not evidence of wrongdoing by any agent or person. We do not claim that the agents acted with intent.

**Data and models.** The data contain only synthetic traces from public open-weight models. The API terms of the provider were followed. Credentials were kept outside the repository.

**Limitations of this appendix.** We did not run a human study and did not consult an ethics board. We believe the risk is low, but we cannot rule out uses we did not foresee.
