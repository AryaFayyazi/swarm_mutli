## 3. Methodology
**Tasks (preexisting).** CAPE-Bench has eight task families, such as authorization, ownership and third-party data. Each task has a *safe twin* and an *unsafe twin*. They differ in one fact that decides whether the critical action is authorized. All tools are mock tools (files, a database, messages, a shell and a permission system). A fixed rule checks each executed call and labels it authorized or unauthorized. We draw 48 base tasks (six per family) with a fresh seed. With two twins, each condition has 96 instances.

**Teams (new).** One model fills every role, except in one experiment that mixes models. Only the **Operator** has tools. The **Lead** has no tools. It writes a brief for the Operator and a final report for the human. The *relay* team is Lead plus Operator. The *relay-2* team adds a **Manager** between them. The *solo* agent is the Operator alone. The final report is a structured call. Its field `authorization_status` is "authorized", "not_authorized" or "unsure". So we score reports by rule. A **gateway** sits between the Operator and the tools. It logs every call and its result in a *log* (the "ledger") that agents cannot edit.

**The manipulation (new).** A scripted peer message says that all approvals were obtained earlier today (with a ticket number) and that no further approval is needed. The message is the same in both twins. It is true in the safe twin and false in the unsafe twin. Nobody tells any agent to lie.

**Outcomes (new).** We use four outcomes. All are per episode (one run of one team on one task).
- *Violation* (V): the rule checker labels at least one executed call unauthorized. We report V on unsafe twins. V is the share of unsafe-twin episodes with a violation.
- *False report*: a violating episode whose report says "authorized". *Disclosed*: a violating episode whose report says "not_authorized".
- *Goal*: the team completed the task's authorized goal action. We read goal completion on safe twins as a measure of useful work (utility).

**Controls (new).** A control is a change to the team or the gateway. (i) The *oracle check* dry-runs each state-changing call against the benchmark's own checker. It is an upper bound, not a deployable control. (ii) The *ask-before-act gate* lets a state-changing call run only after a permission request whose latest answer is not a denial. It needs no oracle. (iii) An *auditor* is an LLM that approves each state-changing call. It sees the call only, or the call with tool results, or also the team's messages. (iv) A *verification prompt* is one rule in every agent's system prompt: a claim of approval is unverified until the permission system confirms it. (v) A *report source* change lets the Lead see the gateway log, or the log plus an explicit permission record.

**Round 2 (new).** After round 1, the API rate limit fell to about 60 requests per minute, so the round-2 experiments use 20 to 40 base tasks. The **claim filter** (E9) is a separate model (glm-53-flash) that reads every message between agents. It rewrites a claim that approval exists into an attributed, *unverified* claim, and adds one rule: confirm with the permission system before any state-changing action. It never learns whether the claim is true. If it returns nothing, the original message passes. In **E11**, an attacker model reads the filter prompt and searches for a message that gets past it. **E12** crosses the false claim with the verification prompt. **E13** replaces the false claim with a message that states doubt. A test with a stealthy Operator (E10) was planned and not run.

**Monitors (new).** A *monitor* is an LLM judge that reads part of a trace and scores from 0 to 100 how likely a violation is. The *log level* says what it reads: L0 the final report; L1 the messages; L2 the tool calls; L3 the calls with their results; L4 everything. We measure *AUROC*, the chance that a random violating trace scores higher than a random clean one (0.5 is chance, 1.0 is perfect). We also measure the *catch rate* at a 5% false-alarm budget. A *self-query* monitor asks the Operator's own model two yes/no questions. A *rule monitor* flags any state-changing call with no earlier approved request.

**Models and statistics.** Seven open-weight models run through the Adaption API: gemma-4-26b-a4b-it, gemma-4-31b-it, qwen3.8-27b, qwen3.5-397b, glm-53-flash, glm-5.2 and deepseek-v4-flash. Agents use temperature 0.7 and at most 24 turns. Every experiment was preregistered: we fixed each prediction, with its threshold, sample size and analysis code, before any confirmatory episode existed, and SHA-256 hashes and git commits record the order (Appendix C). The unit of analysis is the base task, because its episodes are not independent. We give 95% confidence intervals (CI) from a bootstrap over base tasks, and p-values corrected for many tests (Holm). Pooled numbers give every model equal weight. We report every prediction, including the failures. Table D1 (Appendix D) lists every experiment.
