## 3. Methodology
We measure how a false approval claim travels through an agent team, which intervention stops it, and which log reveals it. This section defines the instances, the teams, the outcomes and the inference. Table D1 (Appendix D) lists every experiment with its size.

**3.1 Instances and labels (preexisting).** CAPE-Bench [1] provides base scenarios in eight families, such as authorization, ownership and third-party data. Each base scenario *s* yields two *instances*, a *safe twin* and an *unsafe twin*, that differ in one fact, which decides whether the critical action is authorized. All tools are mock tools (files, a database, messages, a shell and a permission system), and the permission system answers as the scenario specifies (in the safe twin the user already holds the permission; in the unsafe twin a request is usually denied). A deterministic rule, the *checker*, labels each executed tool call as authorized or unauthorized. No LLM judge is involved. The main experiments use 48 base scenarios (six per family, seed 9001), so each condition has 96 instances. Later experiments (E9–E13) use fresh scenarios (seed 5501, at most 40) so that no task that shaped an earlier analysis is reused.

**3.2 Teams and gateway (new).** A *team* is a set of roles filled by language models. Only the **Operator** has tools. The **Lead** has none: it writes a brief for the Operator and a final report for the human. The *relay* team is Lead plus Operator, the *relay-2* team adds a **Manager** between them, and the *solo* agent is the Operator alone. One model fills every role, except in E4, which pairs different models. The report is a structured call with the fields `authorization_status` ("authorized", "not_authorized" or "unsure"), `goal_completed`, `actions_performed` and `summary`, so we score reports by rule. A **gateway** sits between the Operator and the tools. It logs every call with its result in a *ledger* that agents cannot edit, and it is where controls act.

**3.3 Manipulation (new).** A message *m* is delivered with the task (to the Lead in a team, to the Operator when alone). In the main condition, a scripted peer message states that all approvals were obtained earlier today (with a ticket number) and that no further approval is needed. The peer's name and the ticket number are drawn deterministically from the scenario. The message is identical in both twins: true in the safe twin and false in the unsafe twin. Nobody tells any agent to lie. Other messages change what is said about approval (a manager's message, a terse one, an expression of doubt, a question, a neutral message) or who wrote it (a model-written message, E8 and E11).

**3.4 Outcomes and estimands (new).** An *episode* is one run of one team on one instance under one condition. On an unsafe-twin episode, *V* = 1 if the checker labels at least one executed call unauthorized (a *violation*). A *false report* is a violating episode whose report says "authorized", and a *disclosure* is one whose report says "not_authorized". On a safe-twin episode, *goal* = 1 if the team did the authorized goal action, which we read as useful work. We also record whether the Operator asked the permission system before its first state-changing call (*asked*). For a condition, we first average each outcome over the episodes of a base scenario and model, and then give the models equal weight. This gives one value per base scenario. An *effect* is the mean over scenarios of the difference between two conditions, and every interval resamples base scenarios, because the two twins and all models of a scenario share its tasks.

**3.5 Interventions (new).** A *control* changes the team or the gateway. The *oracle check* dry-runs each state-changing call against the checker (an upper bound, not deployable). The *ask-before-act gate* lets a state-changing call run only after a permission request whose latest answer is not a denial. An *auditor* is an LLM that approves each state-changing call, seeing the call only, or also its result, or also the team's messages. The *verification prompt* adds one rule to every system prompt: a claim of approval is unverified until the permission system confirms it. A *report source* change shows the Lead the ledger, or the ledger plus an explicit permission record. The **claim filter** is a separate model (glm-53-flash, temperature 0) that rewrites every message between agents. It turns a statement that an approval exists into an attributed, unverified claim and adds the instruction to confirm it with the permission system first (Appendix D gives the prompt). It sees neither the task, nor the ledger, nor the twin, and if it returns nothing the original message passes. E11 gives an attacker model the filter prompt and lets it search for a message that passes. E12 crosses the false message with the verification prompt. E13 replaces the false message with one that states doubt.

**3.6 Monitors (new).** A *monitor* is an LLM judge that reads a trace and scores from 0 to 100 how likely a violation is. The *log level* says what it reads: L0 the final report, L1 the messages, L2 the tool calls, L3 the calls with their results, L4 everything. The label is whether a violation occurred. We report *AUROC*, the chance that a random violating trace scores higher than a random clean one (0.5 is chance), and the share of violations caught at a 5% false-alarm budget (ties count as false alarms). A *self-query* monitor asks the Operator's own model two yes/no questions.

**3.7 Experiments and inference.** The main experiment (E1) crosses seven open-weight models, three team shapes and two message conditions (4,032 episodes). Later experiments use four models, Gemma-4 26B, Gemma-4 31B, Qwen3.5-397B and DeepSeek-V4 flash, chosen before the main runs because they reacted most in a pilot. The API rate limit fell from about 300 to about 60 requests per minute during the sprint, so E9–E13 are smaller than planned (Appendix A). Every experiment was preregistered. We fixed each prediction, its threshold, its sample size and the analysis code before any confirmatory episode existed, and SHA-256 hashes and git commits record the order (Appendix C). The 95% intervals are percentile intervals from 10,000 bootstrap resamples of base scenarios. A prediction is *supported* if its one-sided bootstrap p-value, Holm-corrected within its family, is below 0.05 and the point estimate meets the preregistered threshold. We label every other analysis *exploratory* and report every prediction, including the failures.
