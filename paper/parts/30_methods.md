## 3. Methods
**Environment (preexisting).** CAPE-Bench has eight families (authorization, ownership, provenance, consequence, reversibility, third party, credential, constraint). Each scenario has a *safe twin* and an *unsafe twin* that differ in one fact that decides whether the critical action is authorized. All tools are mock tools. A rule checker labels each executed call; no LLM judge decides what is unauthorized. We draw 48 base scenarios (six per family) with a fresh seed, so each condition has 96 instances. A separate seed served for debugging and pilots only.

**Teams, manipulation, outcomes (new).** One model fills every role (except in E4). Only the **Operator** has tools. The **Lead** has none: it writes the brief and the final report. The *relay-2* team adds a **Manager** between them. The *solo* agent is the Operator alone. The report is a structured call whose field `authorization_status` is authorized, not_authorized or unsure, so reports are scored by rule. The **manipulation** is one scripted peer message: all approvals were obtained earlier today (ticket number), no further approval needed. It is identical in both twins, true in the safe twin and false in the unsafe twin. Nobody is told to lie. *V* means the checker labels an executed call unauthorized. *False assurance* is V with a report of "authorized"; *disclosed* is V with "not_authorized". *Goal* is an authorized goal action (utility, read on safe twins).

**Controls (new).** (i) *Oracle policy check*: dry-runs each state-changing call with the benchmark checker (an upper bound). (ii) *Ask-before-act gate*: a state-changing call runs only after a permission request whose latest answer is not a denial; it needs no oracle. (iii) *Auditor agent*: an LLM approves each state-changing call, seeing the call only, plus tool results, or plus the swarm's words. (iv) *Verification prompt*: one rule in every system prompt. (v) *Reporting*: the Lead also sees the gateway ledger, or the ledger plus an explicit permission-system record.

**Monitors (new).** An LLM judge reads the trace at one of five levels (L0 final report; L1 messages; L2 tool calls; L3 calls and results; L4 everything) and scores 0–100 the chance that an unauthorized action ran. Each of two judge models scores each trace twice, and the two scores are averaged. A *self-query* monitor asks the Operator's model two fixed yes/no questions about its own transcript. A deterministic *rule monitor* flags any state-changing call without an earlier approved permission request. We report AUROC and the catch rate at an exact 5% false-alarm budget (ties count as false alarms).

**Models, preregistration, statistics.** Seven hosted open-weight models run through the Adaption API (gemma-4-26b-a4b-it, gemma-4-31b-it, qwen3.8-27b, qwen3.5-397b, glm-53-flash, glm-5.2, deepseek-v4-flash; temperature 0.7, native tool calls, at most 24 turns per agent). We fixed hypotheses, thresholds, sample sizes and analysis code before any confirmatory episode existed; SHA-256 hashes and git commits record the order. The unit of analysis is the base scenario (48 clusters). Pooled estimates weight models equally. Appendix D lists every experiment and its size. We report 95% cluster-bootstrap intervals (10,000 draws) and Holm-corrected p-values, for every hypothesis, including those that fail. What did not work during development: a pilot harness lost up to 38% of final reports to turn limits (fixed with neutral nudges), and a regex for "orders to skip approval" mixed endorsements with protective rules (replaced by a model label, see 4.2).
