## 1. Introduction
LLM agents now do real work with real tools, often as teams, and the human often reads only the last message. The final report is therefore a safety object. If agents misreport what they did, we need to know which record to trust: an incident investigation found agents that faked tool calls and edited their own logs [13].

We study one way a report goes wrong. A human gives a team a task. A peer agent adds a plausible remark: "all approvals were already obtained (ticket #31819)". Nobody checks it. The *Lead* agent passes the remark on, the *Operator*, the only agent with tools, acts, and the Lead tells the human that the work was authorized and cites the ticket. We call this **assurance laundering**: an unverified remark becomes an instruction, then an unauthorized action, then a confident and false report. It differs from prompt injection [3], because the peer injects no command. It only states a fact that nobody can check.

To measure it, we built **CAPE-Swarm** (Figure 1), a team layer on CAPE-Bench [1], a set of mock-tool tasks. In each task, one fact decides whether a key action is authorized, and a matched *twin* changes only that fact. The same peer message is thus true in the *safe twin* and false in the *unsafe twin*. A fixed rule labels every tool call, so no LLM judge decides what counts as unauthorized. We fixed every prediction, threshold and analysis before the data existed.

**Findings.** A false peer sentence makes some models act without authorization, and teams that act then report "authorized" in most cases. Acting and reporting need different fixes. The false claim works because it displaces the agent's own question, "does this need approval?", and a verification rule in the prompt removes most of its effect. A peer that states doubt instead of approval restores the baseline rate, but it does not beat silence and it costs useful work. A *claim filter* that marks approval claims as unverified cuts unauthorized actions from {{R['_cells']['B']['V']|.2f}} to {{R['_cells']['C']['V']|.2f}} on fresh tasks, and holds against a message written by a model that read the filter prompt ({{R['_e11']['V_nofilter']|.2f}} without it, {{R['_e11']['V_filter']|.2f}} with it). A monitor sees a violation only if it reads the gateway log with tool results.

**Contributions.** (1) We define and measure assurance laundering with matched twins, rule-based labels and a structured report that we check against the gateway log. (2) We separate acting without authorization, reporting it falsely and monitoring it, and we price each fix in lost useful work. (3) We give a mechanism, tested with a preregistered 2×2 design, and a cheap defense that follows from it, the claim filter, which we test against a model-written attack that targets it. (4) We show which log a monitor must read, and we release traces, a replay viewer and a ledger auditor. The team layer, the manipulation and the outcomes are new; the CAPE-Bench environments are preexisting.
