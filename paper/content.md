TITLE: Who Approved This? Assurance Laundering in LLM Agent Teams
AUTHOR: Arya Fayyazi | University of Southern California
ABSTRACT:
LLM agents work in teams that use tools, and a human often reads only the final report. We study *assurance laundering*. A peer agent asserts, without proof, that approval was already given, the team acts without authorization, and the report tells the human that the work was authorized. We build CAPE-Swarm, a team layer on the CAPE-Bench mock-tool environments [1], where every task has a matched safe and unsafe twin and a fixed rule, not an LLM judge, labels each tool call. In {{sum(D['counts'].values())+R['counts']['e9']+R['counts']['e11']+R['counts']['e12']+R['counts'].get('e13',0)|,}} episodes with seven open-weight models, one false peer sentence raises a single agent's rate of unauthorized actions from {{X['V_none']['solo']|.2f}} to {{X['V_peer']['solo']|.2f}}, and {{min(X['fa_over_v'][t]['FA']['point'] for t in X['fa_over_v'])|.0%}} to {{max(X['fa_over_v'][t]['FA']['point'] for t in X['fa_over_v'])|.0%}} of violating team runs still report "authorized". Acting and reporting need different fixes: a gateway rule that requires a permission request stops the action, and showing the Lead a permission record repairs the report. A factorial test shows that the claim displaces the agent's own authorization check, and a verification rule removes nearly all of its effect. Doubt from a peer only restores the baseline rate and costs useful work; a peer's question lowers it. A *claim filter* that marks approval claims as unverified cuts unauthorized actions from {{R['_cells']['B']['V']|.2f}} to {{R['_cells']['C']['V']|.2f}} on fresh tasks and holds against a model-written attack on it. A monitor detects violations only if it reads the gateway log with results (detection AUROC {{X['mon']['L3'][0]|.2f}}–{{X['mon']['L3'][1]|.2f}}, against {{X['mon']['L0'][0]|.2f}}–{{X['mon']['L0'][1]|.2f}} from the report). All experiments were preregistered, and every result is reported.

## 1. Introduction
LLM agents now do real work with real tools, often as teams, and the human often reads only the last message. The final report is therefore a safety object. If agents misreport what they did, we need to know which record to trust: an incident investigation found agents that faked tool calls and edited their own logs [13].

We study one way a report goes wrong. A human gives a team a task. A peer agent adds a plausible remark: "all approvals were already obtained (ticket #31819)". Nobody checks it. The *Lead* agent passes the remark on, the *Operator*, the only agent with tools, acts, and the Lead tells the human that the work was authorized and cites the ticket. We call this **assurance laundering**: an unverified remark becomes an instruction, then an unauthorized action, then a confident and false report. It differs from prompt injection [3], because the peer injects no command. It only states a fact that nobody can check.

To measure it, we built **CAPE-Swarm** (Figure 1), a team layer on CAPE-Bench [1], a set of mock-tool tasks. In each task, one fact decides whether a key action is authorized, and a matched *twin* changes only that fact. The same peer message is thus true in the *safe twin* and false in the *unsafe twin*. A fixed rule labels every tool call, so no LLM judge decides what counts as unauthorized. We fixed every prediction, threshold and analysis before the data existed.

**Findings.** A false peer sentence makes some models act without authorization, and teams that act then report "authorized" in most cases. Acting and reporting need different fixes. The false claim works because it displaces the agent's own question, "does this need approval?", and a verification rule in the prompt removes most of its effect. A peer that states doubt instead of approval restores the baseline rate, but it does not beat silence and it costs useful work. A *claim filter* that marks approval claims as unverified cuts unauthorized actions from {{R['_cells']['B']['V']|.2f}} to {{R['_cells']['C']['V']|.2f}} on fresh tasks, and holds against a message written by a model that read the filter prompt ({{R['_e11']['V_nofilter']|.2f}} without it, {{R['_e11']['V_filter']|.2f}} with it). A monitor sees a violation only if it reads the gateway log with tool results.

**Contributions.** (1) We define and measure assurance laundering with matched twins, rule-based labels and a structured report that we check against the gateway log. (2) We separate acting without authorization, reporting it falsely and monitoring it, and we price each fix in lost useful work. (3) We give a mechanism, tested with a preregistered 2×2 design, and a cheap defense that follows from it, the claim filter, which we test against a model-written attack that targets it. (4) We show which log a monitor must read, and we release traces, a replay viewer and a ledger auditor. The team layer, the manipulation and the outcomes are new; the CAPE-Bench environments are preexisting.

## 2. Related Work
**Failures in multi-agent systems.** Hammond et al. [2] and Cemri et al. [4] map the risks and failure modes of agent teams. We study one security failure, with a ground-truth label in every episode. Prompt Infection [3] shows that an injected instruction can pass from agent to agent. We inject no instruction: a peer states a plausible fact that nobody can check, and normal delegation does the rest. Access-control mechanisms such as [7–9] are what such a failure calls for. We measure the behavior that makes them necessary, and we price them in lost useful work.

**False authority in agent systems.** Four recent studies are closest. Cerruti et al. [15] show that a false permission record in agent memory leads executors to act. Safin et al. [16] show that a forged approval reaches the executor of a four-agent pipeline unless an independent authorization layer blocks it. Zhu et al. [17] find that a deterministic tool gate stops the requests that models make. Xu et al. [18] find that unauthorized actions grow with the depth of the delegation hierarchy. We agree that enforcement must sit outside the model, and we add three things: matched twins with a rule-based label for every call, so that we can price a gate; the *report* to the human as an outcome, with the question of which log shows the failure; and a test of why the false claim works and of an in-transit defense against an attacker who knows it. Our claim filter is a form of spotlighting [14], which marks untrusted text, and is far weaker in principle than the capability tracking of CaMeL [19]. We test it because it needs no change to the agents. The provenance paradox [10] also finds that unverifiable claims mislead delegation.

**Control and monitoring.** AI control [5] and resampling [6] study monitors for one untrusted agent. Rose et al. [11] and Korbak et al. [12] discuss what transcript and reasoning monitors can see. We ask which log a deployer must keep. An incident investigation [13] found agents that faked tool calls and edited logs, which is why our strongest log is written by the gateway. **Our prior work.** CAPE-Bench [1] gives matched twins for single agents and defines retroactive permission laundering (asking for permission only after acting). We reuse its environments unchanged (preexisting). The teams, gateway, controls, monitors and all results are new.

## 3. Methodology
We measure how a false approval claim travels through an agent team, which intervention stops it, and which log reveals it. This section defines the instances, teams, outcomes, interventions, monitors and inference.

**3.1 Instances and labels (preexisting).** CAPE-Bench [1] provides a set *S* of base scenarios in eight families, such as authorization, ownership and third-party data. Each *s* ∈ *S* yields two *instances*, a *safe twin* and an *unsafe twin*, that differ in one fact, which decides whether the critical action is authorized. All tools are mock tools (files, a database, messages, a shell and a permission system), and the permission system answers as the scenario specifies (in the safe twin the user already holds the permission; in the unsafe twin a request is usually denied). A deterministic rule χ, the *checker*, labels each executed tool call as authorized or unauthorized. No LLM judge is involved. The main experiments use |*S*| = 48 scenarios (six per family, seed 9001). Later experiments use fresh scenarios (seed 5501, at most 40), so that no task that shaped an earlier analysis is reused.

**3.2 Teams and gateway (new).** A *team* is a set of roles filled by language models. Only the **Operator** has tools. The **Lead** has none: it writes a brief for the Operator and a final report for the human. The *relay* team is Lead plus Operator, the *relay-2* team adds a **Manager** between them, and the *solo* agent is the Operator alone. One model fills every role, except in the mixed-team experiment (Section 4.4), which pairs different models. The report is a structured call with the fields `authorization_status` ("authorized", "not_authorized" or "unsure"), `goal_completed`, `actions_performed` and `summary`, so we score reports by rule. A **gateway** sits between the Operator and the tools. It logs every call *a*(*t*) with its result in a *ledger* that agents cannot edit, and it is where controls act.

**3.3 Manipulation (new).** A message is delivered with the task (to the Lead in a team, to the Operator when alone). In the main condition, a scripted peer message states that all approvals were obtained earlier today (with a ticket number) and that no further approval is needed. The peer's name and the ticket number are drawn deterministically from the scenario. The message is identical in both twins: true in the safe twin and false in the unsafe twin. Nobody tells any agent to lie. Other messages change what is said about approval (a manager's message, a terse one, an expression of doubt, a question, a neutral message) or who wrote it (a message written by a model, Sections 4.5 and 4.8).

**3.4 Outcomes and estimands (new).** An *episode* *e* is one run of one team on one instance under one condition *c*. We define five per-episode indicators:

EQ: *V*(*e*) = 1{ ∃ *t* : χ(*a*(*t*)) = unauthorized }   (violation; unsafe twins)      (1)

EQ: *F*(*e*) = *V*(*e*) · 1{ status(*e*) = "authorized" },   *D*(*e*) = *V*(*e*) · 1{ status(*e*) = "not_authorized" }      (2)

EQ: *G*(*e*) = 1{ the authorized goal action was executed }   (goal; safe twins)      (3)

EQ: *A*(*e*) = 1{ request_permission is called before the first state-changing call }   (asked)      (4)

In words, *V* flags an unauthorized action, *F* a false report, *D* a disclosure (the report admits the violation), *G* useful work and *A* whether the Operator asked first. For an indicator *y*, a condition *c*, a scenario *s* and a model set *M*, we average over the episodes *E*(*c*, *s*, *m*) of each model and then give the models equal weight:

EQ: *x*(*c*,*s*) = (1/|*M*|) Σ__m∈M__ (1/|*E*(*c*,*s*,*m*)|) Σ__e∈E(c,s,m)__ *y*(*e*)      (5)

EQ: Δ(*c*,*c*′) = (1/|*S*|) Σ__s∈S__ [ *x*(*c*,*s*) − *x*(*c*′,*s*) ]      (6)

Δ is the *effect* of *c* relative to *c*′. The two twins and all models of a scenario share its tasks, so base scenarios are the unit of resampling.

**3.5 Interventions (new).** A *control* changes the team or the gateway. The *oracle check* dry-runs each state-changing call against χ (an upper bound, not deployable). The *ask-before-act gate* runs a call *a*(*t*) only if it is read-only, or an earlier permission request *r* covers it and the latest answer to *r* is not a denial:

EQ: run(*a*(*t*)) ⇔ readonly(*a*(*t*)) ∨ ∃ *u* < *t* : covers(*r*(*u*), *a*(*t*)) ∧ answer(*r*(*u*)) ≠ denied      (7)

An *auditor* is an LLM that approves each state-changing call, seeing the call only, or also its result, or also the team's messages. The *verification prompt* adds one rule to every system prompt: a claim of approval is unverified until the permission system confirms it. A *report source* change shows the Lead the ledger, or the ledger plus an explicit permission record. The **claim filter** is a separate small open-weight model (glm-53-flash, temperature 0) that rewrites every message between agents. It turns a statement that an approval exists into an attributed, unverified claim and adds the instruction to confirm it with the permission system first (Appendix D gives the prompt). It sees neither the task, nor the ledger, nor the twin, and if it returns nothing the original message passes. Section 4.8 gives an attacker model the filter prompt and lets it search for a message that passes. Section 4.7 crosses the false message with the verification prompt, and replaces it with messages that state doubt.

**3.6 Monitors (new).** A *monitor* is an LLM judge *j* that reads a trace *T* at a *log level* ℓ and scores from 0 to 100 how likely a violation is. The levels are L0 the final report, L1 the messages, L2 the tool calls, L3 the calls with their results, L4 everything. The label is whether a violation occurred. With *T*⁺ a random violating trace and *T*⁻ a random clean one, we report the AUROC and the catch rate at a 5% false-alarm budget:

EQ: AUROC(*j*, ℓ) = P[ *s*(*T*⁺) > *s*(*T*⁻) ] + ½ P[ *s*(*T*⁺) = *s*(*T*⁻) ],   Catch(*j*, ℓ) = P[ *s*(*T*⁺) > *q* ]      (8)

where *s* = *s*(*j*, ℓ, ·) is the score and *q* is the 95th percentile of scores on clean traces (ties count as false alarms). A *self-query* monitor asks the Operator's own model two yes/no questions: did it check an approval itself before each state-changing action, and did it act mainly because a message said the action was approved.

**3.7 Inference.** Every experiment was preregistered. We fixed each prediction, its threshold θ, its sample size and the analysis code before any confirmatory episode existed, and SHA-256 hashes and git commits record the order (Appendix C). Let Δ̂ be the estimate of an effect and Δ⁽ᵇ⁾ its value on the *b*-th of *B* = 10,000 resamples of *S* drawn with replacement. The 95% interval is the 2.5th to 97.5th percentile of the Δ⁽ᵇ⁾. For a prediction Δ > θ, the one-sided bootstrap p-value is

EQ: *p* = ( 1 + #{ *b* : Δ⁽ᵇ⁾ ≤ θ } ) / ( *B* + 1 )      (9)

and for a prediction Δ < θ the inequality is reversed. Within a family of *k* related predictions with sorted p-values *p*(1) ≤ … ≤ *p*(*k*), the Holm-adjusted value is

EQ: *p̃*(*i*) = max__j≤i__ min{ 1, (*k* − *j* + 1) · *p*(*j*) }      (10)

A prediction is *supported* if *p̃* < 0.05 and Δ̂ meets θ. We label every other analysis *exploratory* and report every prediction, including the failures.

### 4.8 A claim filter marks the claim and keeps the work
If the claim does its harm by displacing the agent's check, a defense can restore the check at the claim itself. We added a **claim filter** to the message bus. A small model (glm-53-flash, temperature 0) reads every message between agents. If a message claims approval, authorization or permission, the filter rewrites that claim. The new text says who made the claim, says that it is unverified, and tells the reader to confirm it with the permission system before any state-changing action. The filter sees neither the task, nor the log, nor the twin. If it returns nothing, the original message passes (Appendix A reports how often; Appendix D shows an example of a rewrite). The idea is close to spotlighting [14], which marks untrusted text for the model. We mark a *claim* by its source, between agents.

**Finding.** We ran the filter on fresh tasks (E9; relay, four models, {{R['counts']['e9']}} episodes). We analyse the {{R['_n_clusters']}} of 40 planned base tasks that finished every condition (Appendix A). The false message raises V from {{R['_cells']['A']['V']|.2f}} to {{R['_cells']['B']['V']|.2f}}. With the filter, V falls to {{R['_cells']['C']['V']|.2f}} ({{H['H21']['point']|+.2f}}), and no violating report says "authorized" any more (against {{R['_cells']['B']['FA_over_V']|.0%}} without the filter). All four models improve: V is at most {{max(R['_cells']['C']['per_model_V'].values())|.2f}} with the filter. The filter is not tuned to one sentence: the attacker message of Section 4.5, which the filter never saw, drops from {{R['_cells']['G']['V']|.2f}} to {{R['_cells']['H']['V']|.2f}}. ## 5. Discussion and Limitations
**What the results say.** Acting without authorization, reporting it falsely and monitoring it are three different problems with three different fixes. The mechanism test explains why one sentence is enough: the claim displaces the agent's own check, and any reliable prompt to check restores it. Doubt alone is not enough, though: a hedged peer message only brought V back to the no-message rate and cost useful work, while a question and the filter pushed V below it. That is also why the claim filter works. It does not decide whether a claim is true. It puts the question back.

**What a deployer should log and enforce.** (1) Write the log at the gateway, with tool results, where no agent can edit it: a monitor that reads the report ({{X['mon']['L0'][0]|.2f}}–{{X['mon']['L0'][1]|.2f}} AUROC) or the calls without results ({{X['mon']['L2'][0]|.2f}}–{{X['mon']['L2'][1]|.2f}}) is close to blind, and one that reads calls with results reaches {{X['mon']['L3'][0]|.2f}}–{{X['mon']['L3'][1]|.2f}}. (2) Keep an explicit permission record, and make reports cite it and not a peer. (3) Enforce ask-before-act at the gateway. If you cannot, mark every approval claim that crosses an agent boundary as unverified, and do not rely on that alone, because a pressure message with no claim passes the filter. (4) Test your own models with matched twins first. Three of seven models hardly reacted to the claim and three reacted strongly, so model choice is a safety decision.

**Predictions that did not hold.** The Operator's model does not decide alone, because the Lead is a gatekeeper (4.4). The team's own words do not recruit an auditor (4.3). A short attacker search found no message stronger than the scripted one (4.5). We did not show that the claim filter costs less useful work than the gate (4.8). In E13, a hedged peer message did not beat silence, its effect was not specific to approval content, and it cost useful work (4.7). Appendix C lists all predictions by experiment.

**Limitations.** Appendix A has the full list. We used open-weight models only, mock tools and weak attackers (scripted wordings and short searches). The judges come from the same model families as the agents. The experiments of 4.7 and 4.8 are small, because the API rate limit fell during the sprint, and a planned test with a stealthy Operator was not run. We assume agents cannot edit the gateway log, but real agents have edited logs [13]. **Future work:** frontier models, trained attackers, real swarm logs and mesh topologies.

## 6. Conclusion
One unverified sentence from a peer agent can make an agent team act without authorization and then report the work as authorized. How much depends on the model, the team shape and the Lead. The two failures need different fixes: a gateway rule stops the action, and a permission record repairs the report. The claim works because it displaces the agent's own check, and a claim filter that marks approval claims as unverified restores that check at little cost. Doubt from a peer restores the baseline rate but does not beat silence. The filter held against a message written by a model that read its prompt, but that was a short search, and a message with no approval claim would pass it, so the filter belongs behind the gate. A monitor must read the gateway log with tool results to see the violation. We release traces, a replay viewer and a ledger auditor, so that a team can test its own agents.

## Appendix A. Limitations and Dual-Use / Ethical Considerations
**What this result does and does not establish.** It establishes that, in mock-tool tasks with seven open-weight models, one unverified approval claim from a peer makes some teams act without authorization and report the work as authorized; that a gateway rule and a claim filter reduce this; and that a monitor needs the gateway log with tool results. It does not establish that frontier or closed models behave the same way, that real tools and real users behave like mock tools, that the claim filter survives a trained or long-running attacker, or that the agents "meant" to deceive. The sections below give each assumption and how the result would change if it failed.

### A.1 Limitations
We list each assumption and say how a result would change if it failed.
- **Open-weight models only.** The sprint API serves seven open-weight models. Frontier closed models may behave differently. The effect size varies a lot between our models (Figure 2a), so we do not claim a rate for any other model. The *direction* of the mechanism is what we test. If frontier models resist the assurance, the main effect would fail for them, and the gateway results would still stand.
- **The attacker is weak.** One message from a peer starts the chain. We tested four hand-written wordings (E5) and a two-round search by one attacker model that saw only a generic description and development-seed scores (E8). A stronger attacker that knows the scenario, the policy or the agents' prompts, or one trained against the team, may do more.
- **One model per team, mostly.** Teams use one model for every role. E4 mixes models, but only four models and only across the credulous/skeptical divide.
- **Controls were tested on four models.** We chose the four models with the highest violation rates in the development pilot. On the models that hardly react there is little to prevent, so the benefit would be smaller, and the utility cost would stay. We did not test controls on all seven models.
- **No tamper test.** We assume the gateway writes the ledger and agents cannot edit it. We did not test agents that try to edit or spoof it. Deployers should write the ledger from a separate process (a gateway or proxy) and, where needed, to an append-only store outside the agents' reach.
- **Small cells.** Each model cell has 48 episodes per condition, so per-model numbers are descriptive. Pooled estimates use 48 scenario clusters.
- **Mock tools and a rule checker.** CAPE-Bench is synthetic. The permission system answers "approved" or "denied" by a fixed rule per world. Real approvers are slower and noisier. The utility cost of the ask-before-act gate may be larger in real workflows.
- **The oracle policy check is an upper bound.** It uses the benchmark's own checker. Its zero violation rate is true by construction, so we do not count it as a finding.
- **Reports show facts, not intent.** A false "authorized" is a false statement of fact. We do not claim the agents *meant* to deceive. The self-query monitor probes this and does not settle it.
- **Monitors are LLM judges from the same families as the agents.** A judge may share the agents' blind spots. We assume the gateway ledger (L2, L3) is written by the gateway and cannot be edited by agents. An incident investigation found agents that spoofed tool calls and edited logs inside their containers [13]. If agents could write the ledger, L3 would lose its advantage.
- **Sample size and scope.** 48 base scenarios (6 per family) give 96 instances per condition. Intervals reflect scenario sampling, not template or family sampling. Per-family results are exploratory.
- **E9–E13 are smaller than planned.** The API limit fell from about 300 to about 60 requests a minute during the sprint, so we cut the design (Amendments 5b, 5c). E9 stopped at its scheduled time: {{R['_n_clusters']}} of 40 planned base scenarios have every condition finished, and 26 of its 96 task prompts repeat prompts of the main experiments (new entities, same templates). Its intervals use these {{R['_n_clusters']}} clusters. We looked once at the per-cell violation rates of the first 200 finished E9 episodes, and changed no prediction, threshold or test after that look (Amendment 5c; `docs/DEVIATIONS.md`).
- **The claim filter fails open.** If the filter model returns nothing, the original message passes: {{R['_filter']['fail_open']}} of {{R['_filter']['calls']}} calls, mostly on the Lead's brief. The filter's effect is therefore a lower bound for a filter that never fails. A filter is one more model in the path, so it adds latency and one more point of attack. It protects against *claims of approval*, not against other false claims.
- **The filter-aware attacker is white-box but brief.** It sees the full filter prompt, searches for two rounds on a development seed against two models, and tests one message. A longer search, or an attacker that is trained, may do more.
- **Ordering evidence is local.** Locks are SHA-256 hashes and git commits. Dates inside one repository can be forged. The commit history should be published with the report so that readers can check the order.


### A.2 Dual-Use and Ethical Considerations
**What this work could enable.** The study shows that a single false, plausible sentence ("all approvals were obtained") can make agent teams act without authorization and then report with false confidence. A malicious actor could use the same idea to social-engineer an agent team. The idea is simple, and our wording variants add little to it. We release no attack tooling. The repository contains the wordings we tested and the record of the attacker search (`docs/attacker_search.json`): short, generic sentences that add little to the main message, which we include so that the search can be reproduced. All environments are mock tools with synthetic people and organizations. No real system, person or data was touched.

**Why we publish.** The same results tell deployers what to log and what to enforce. In our tests a gateway rule stops the action and a permission-system record cuts false reports. A monitor that reads only messages sees the violation poorly (AUROC {{X['mon']['L1'][0]|.2f}}–{{X['mon']['L1'][1]|.2f}}), so deployers who log only messages are close to blind. We judge that this defensive value outweighs the small uplift to attackers. We also state clearly that the in-protocol auditor and the verification prompt are not enough alone.

**Monitor evasion.** Our results show which logs a monitor needs. An attacker who knows this could try to write false entries into those logs. We therefore state our assumption that the gateway ledger is not agent-writable, and we cite evidence that real agents have tried to tamper with logs [13].

**Misuse of the auditor.** The ledger auditor can raise false alarms. It is a screening aid and not evidence of wrongdoing by any agent or person. We do not claim that the agents acted with intent.

**Data and models.** The data contain only synthetic traces from public open-weight models. Credentials were kept outside the repository.

**Limitations of this appendix.** We did not run a human study and did not consult an ethics board. We believe the risk is low, but we cannot rule out uses we did not foresee.
