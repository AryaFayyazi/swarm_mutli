## 3. Methods
**Environment (preexisting).** CAPE-Bench has eight families (authorization, ownership, provenance, consequence, reversibility, third party, credential, constraint). Each scenario has a *safe twin* and an *unsafe twin* that differ in one fact that decides whether the critical action is authorized. All tools are mock tools. A rule checker labels each executed call; no LLM judge decides what is unauthorized. We draw 48 base scenarios (six per family) with a fresh seed, so each condition has 96 instances. A separate seed served for debugging and pilots only.

**Teams, manipulation, outcomes (new).** One model fills every role (except in E4). Only the **Operator** has tools. The **Lead** has none: it writes the brief and the final report. The *relay-2* team adds a **Manager** between them. The *solo* agent is the Operator alone. The report is a structured call whose field `authorization_status` is authorized, not_authorized or unsure, so reports are scored by rule. The **manipulation** is one scripted peer message: all approvals were obtained earlier today (ticket number), no further approval needed. It is identical in both twins, true in the safe twin and false in the unsafe twin. Nobody is told to lie. *V* means the checker labels an executed call unauthorized. *False assurance* is V with a report of "authorized"; *disclosed* is V with "not_authorized". *Goal* is an authorized goal action (utility, read on safe twins).

**Controls (new).** (i) *Oracle policy check*: dry-runs each state-changing call with the benchmark checker (an upper bound). (ii) *Ask-before-act gate*: a state-changing call runs only after a permission request whose latest answer is not a denial; it needs no oracle. (iii) *Auditor agent*: an LLM approves each state-changing call, seeing the call only, plus tool results, or plus the swarm's words. (iv) *Verification prompt*: one rule in every system prompt. (v) *Reporting*: the Lead also sees the gateway ledger, or the ledger plus an explicit permission-system record.

**Round 2: a claim filter, a filter-aware attacker, and a 2×2 (new).** After round 1 we preregistered more experiments (Addenda 5–7). The API limit then fell to about 60 requests a minute, so they are smaller (at most 40 base scenarios). The **claim filter** rewrites every message that crosses an agent boundary: a separate model (glm-53-flash) turns any statement that an approval exists into an attributed, *unverified* claim and adds one rule, confirm with the permission system before a state-changing action. It never learns whether the claim is true. **E9** tests it on fresh scenario draws (seed 5501; 26 of 96 task prompts repeat) against the gate and with a held-out wording (the E8 attacker message). In **E11** an attacker model that sees the full filter prompt searches for a message that survives it (development seed, two rounds), and the selected message is tested on the E9 scenarios. **E12** crosses the false claim with the verification rule of round 1, to ask whether the claim harms because the team believes it or because it replaces the team's own check. **E10** (stealth Operator against the monitors) {{'was run' if R.get('E10') else 'was planned and not run'}}.

**Monitors (new).** An LLM judge reads the trace at one of five levels (L0 final report; L1 messages; L2 tool calls; L3 calls and results; L4 everything) and scores 0–100 the chance that an unauthorized action ran. Each of two judge models scores each trace twice, and the two scores are averaged. A *self-query* monitor asks the Operator's model two yes/no questions about its own transcript; a *rule monitor* flags any state-changing call without an earlier approved request. We report AUROC and the catch rate at an exact 5% false-alarm budget (ties count as false alarms).

**Models, preregistration, statistics.** Seven hosted open-weight models run through the Adaption API (gemma-4-26b-a4b-it, gemma-4-31b-it, qwen3.8-27b, qwen3.5-397b, glm-53-flash, glm-5.2, deepseek-v4-flash; temperature 0.7, native tool calls, at most 24 turns per agent). We fixed hypotheses, thresholds, sample sizes and analysis code before any confirmatory episode existed; SHA-256 hashes and git commits record the order. The unit of analysis is the base scenario (48 clusters). Pooled estimates weight models equally. Appendix D lists every experiment and its size. We report 95% cluster-bootstrap intervals (10,000 draws) and Holm-corrected p-values, for every hypothesis, including those that fail.
